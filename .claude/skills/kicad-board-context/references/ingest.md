# Ingest — trust rules and caveats

How to interpret what the extractors produce, what they *cannot* see, and the
failure signatures to recognize before reporting findings to the user.

## What extraction is (and isn't)

The extracted `netlist.yaml` is **what the schematic geometry actually says**
— wires, labels, junctions, power symbols resolved into nets. It is not design
intent. On a healthy board the two coincide; on a broken board the *gap*
between them is often the defect. Consequences:

- A short circuit extracts as one merged net (that's what the wires say). If
  a net's pin list mixes functions that shouldn't share copper (an output
  driving into another output, a balance tap on GND), that is a **finding**,
  not an extraction artifact. The extractor won't flag it — reasoning must.
- A missing connection extracts as two separate nets (often one auto-named
  `N$...` singleton). `validate_kicad_sch`'s `single_pin_net` /
  `floating_pin` checks and `verify_netlist` after enrichment surface these.
- `EXTRACTED-FLOATING` entries in `no_connects` are pins with no wire and no
  NC marker. They keep the document loadable, but each is a real review item:
  intentional-but-unmarked, or forgotten.

## Recognize these failure signatures BEFORE reporting errors

### Stale lib_symbols cache (loader drops components)

`load_kicad_sch` resolves placed symbols **only** from the file's embedded
`(lib_symbols)` cache by exact `lib_id` match. A schematic that was hand-built
or received cross-project pastes can have instances whose `lib_id` is missing
from its cache (e.g. cached as `Pololu_Breakout_DRV8825_1`, instance says
`Custom:Pololu_Breakout_DRV8825`). The loader then **drops the component**,
and everything wired to it cascades into false `dangling_wire` /
`disconnected_label` / `floating_pin` errors — observed: 1 stale symbol → 14
false errors. KiCad itself falls back to the library, so our tools over-report
relative to ERC.

**Signature:** a cluster of dangling/disconnected errors all geometrically
around one absent component; `missing_lib_symbol` mentions; a ref present in
`extract_bom` output (regex-based, doesn't need the cache) but absent from
`extract_netlist`'s components.

**Response:** tell the user which symbol's cache is stale (open + re-save in
KiCad refreshes it), rather than reporting the cascade as 14 findings. A
loader library-fallback is on the generator skill's TODO; until it lands this
recognition step is manual.

### Stale instance references (wrong/duplicate refs)

KiCad 8 leaves stale `(instances)` records after re-annotation/merges. The
loader already resolves the active-project reference, but if any KiCad-parsing
tool reports surprising duplicate/odd refs, suspect stale instances first
(see the Validator notes in CLAUDE.md).

### Off-grid geometry (hand-placed symbols)

All the connectivity tooling — and KiCad itself — resolves connections by
coordinate coincidence on the **1.27 mm grid**. A hand-placed symbol or wire
that is off-grid can leave a pin visually touching a wire while electrically
floating. Extraction reports what the coordinates say: an off-grid pin shows
up as `floating_pin` / a singleton net even though the drawing "looks
connected."

**Signature:** a floating/singleton finding where the user says "but it's
clearly connected in KiCad" — check the symbol's `(at x y)` for non-multiples
of 1.27. **Response:** the fix is in KiCad (drag to grid / KiCad's own grid
snap), then re-ingest. This bites the review/edit side, not the bake path —
`bake_bom_fields.py` touches only property text, never geometry.

### Generated-vs-hand-built pin geometry

Schematics generated by `generate_kicad_sch.py` use ±2.54mm pins on Device:C/R
where KiCad's standard symbols use ±3.81mm. A file that *merges* both origins
can show dangling wires at exactly those passives. Real KiCad-authored boards
are unaffected.

## Extractor conventions

- **Auto-named nets** (`N$<ref>_<pin>`): a net with no label, named after its
  first pin (sorted). Deterministic across runs; stable under edits that don't
  touch that net. These are normal in hand-drawn schematics (direct
  wire-to-wire connections); in generator-produced schematics everything is
  labeled, so an auto-name there is itself interesting.
- **Power symbols** become `power_symbols:` + `type: power` on their nets,
  never components. Multi-unit symbols appear once in `components:` with all
  units' pins.
- **`function:` fields** on net pins are the symbol's pin *names* — usually
  the IC's own signal names. They come from the drawing, not a datasheet:
  useful orientation, not verified fact. Verification is what fact cards +
  the answer-blind pinout re-derivation are for (ENRICH phase).
- **BOM blanks are verbatim.** `extract_bom.py` copies fields; a blank
  Manufacturer/MPN means the schematic doesn't carry one. The Stage-9 gates
  (`check_pcbway.py --schematic`, `check_bom_mpn_ready`) are the enforcement;
  extraction just makes the state visible.

## Drift interpretation (reconcile.py)

| Check | Usual meaning | Usual resolution |
|-------|---------------|------------------|
| `missing_on_board` | schematic edited after last F8 sync | user runs F8, re-ingest |
| `board_only_component` (non-mechanical) | part deleted from schematic, not board | user deletes footprint or restores symbol |
| `value_drift` | bench tuning done on the board only, or stale board | ask which side is truth; the other gets updated |
| `footprint_drift` | footprint swapped during layout | usually board is intentional → schematic field is stale |
| `field_not_propagated` | **F8 never ran after fields were added** | run F8; this is the wrong-uploaded-BOM class |
| `field_drift` | fields edited after last sync | run F8 after confirming schematic is right |
| sch-bom drift vs a user-supplied BOM | hand-edited spreadsheet | regenerate the BOM from source, never patch the sheet |

Reconcile reports; the **user** arbitrates. Record accepted drift in
`00_context_pack.md` so a later session doesn't re-raise it.

## Provenance discipline

Every extracted document carries `source_sha256` + `extracted_utc`. The
context pack manifest aggregates them. Re-hash before reasoning; after the
user edits the board (including fixes you suggested), re-ingest and diff —
confirming a fix took is part of the fix.
